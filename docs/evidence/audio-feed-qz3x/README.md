# Browser Proof: the confirm dialog's Escape / light-dismiss RESOLUTION (audio-feed-qz3x)

- Script: scripts/verify_qz3x_confirm_dismiss_browser.ts
- Asserts: the proof is on `/account` with the real dialog client; Escape on a fresh dialog closes it and resolves false; the OK button resolves true; a real backdrop click closes the dialog and resolves false; an approved dialog leaves `returnValue = "confirm"`; and after that approval a later Escape STILL resolves false.
- Run: `deno run --allow-all --unstable-kv scripts/verify_qz3x_confirm_dismiss_browser.ts`

## The hazard this covers

`src/assets/confirm-shared.js` resolved the promise from its `close` listener with
`confirmDialog.returnValue === "confirm"`. `showModal()` does not reset `returnValue`, and an Escape
close or a light-dismiss carries NO result, so the value left behind by an EARLIER dialog survives:
once any confirm had been approved, the next dialog resolved TRUE even when the user pressed Escape.
The caller then performed the destructive action the user had just cancelled.

That is a cross-dialog leak, which is why no existing test saw it: `scripts/account-browser-proof.ts`,
`scripts/regenerate-browser-proof.ts` and `scripts/admin-module-browser-proof.ts` all drive this dialog
but only through OK, and `tests/dialog_test.ts` (light-dismiss fallback) and
`tests/dialog_closedby_test.ts` (the shim closing the dialog) check the CLOSING rather than the
RESOLUTION. Observing the leak also needs TWO dialogs in one page session.

Escape and the backdrop are driven as REAL input events (`Input.dispatchKeyEvent`,
`Input.dispatchMouseEvent`), not synthetic clicks: the dialog declares `closedby="any"` and
light-dismiss is native on current headless Chrome, so a synthetic `.click()` would exercise a
different path from the one a user takes. The three rows that need freshness navigate on purpose -
`returnValue` lives on the element, so a real page load is what clears it, and clearing it by hand
inside the proof would hide the very state being measured.

## The fix it pins

One line immediately before `showModal()`: `confirmDialog.returnValue = "";` - so
`close("confirm")` resolves true, `close("cancel")` resolves false, and a no-result close
(Escape or light-dismiss) leaves `""` and resolves false.

## Negative control (why this row can fail)

Both directions were measured rather than assumed.

- On the UNFIXED tree the hazard row is RED and the run exits 1 with the other six green:
  `STALE SUCCESS LEAKED ACROSS DIALOGS: the user pressed Escape and the caller was told TRUE (returnValue="confirm")`.
- With the comparison mutated to an unconditional `resolve(true)` - the mutation asserted to have
  applied - the proof exits non-zero and THREE rows go red (fresh Escape, light-dismiss, and the
  hazard), so the row is not merely passing after a fix.
